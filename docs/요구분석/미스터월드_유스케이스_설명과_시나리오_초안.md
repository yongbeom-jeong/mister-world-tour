# 미스터 월드 유스케이스 설명과 시나리오 초안

작성일: 2026-10-03  
최종 수정일: 2026-10-05

수정 내용: 이 파일을 so0 팀의 분석산출물 작성 기준으로 지정하고, 허니문 2인 전용 출발과 공동 모집 제외를 사용자 확정 규칙으로 반영했다. 기존 8개 유스케이스 구성과 한글명을 유지하며, ID를 MWT-UC1~MWT-UC8로 통일하고 사용자 지정 담당 분담을 반영했다. 유스케이스 설명서를 분석산출물 양식의 11개 항목으로 재구성했다. MWT-UC1·MWT-UC2·MWT-UC6·MWT-UC7·MWT-UC8의 분석용 시퀀스도를 StarUML 모델과 PNG로 작성하여 해당 설명에 연결했다. 고객은 고객 유형으로, 직원은 직원 유형으로 회원가입하고 선택한 유형에 맞는 역할을 저장하는 규칙을 사용자 확정으로 반영했다. 이미 신청이 있는 여행 상품은 수정할 수 없다는 규칙을 사용자 확정으로 반영했다.

이 파일은 **so0 팀의 분석산출물 작성 기준 문서**다. 고객과 직원의 목표를 8개 유스케이스로 정리하며, 각 유스케이스의 설명 표 아래에 시나리오를 배치하고, 남은 질문은 뒤에서 관리한다. 분석산출물의 설명서·시나리오·유스케이스도·액티비티도는 이 파일을 기준으로 작성한다. 다른 초안이나 기존 그림과 내용이 다르면 이 파일에 맞춰 보완하거나 다시 작성한다. 확정 규칙과 아직 검토 중인 세부 정책은 본문의 상태 표기로 구분한다.

### 신청과 이력 규칙

- 단골은 **최근 3년 이내 여행을 3회 이상 완료한 고객**이다. 신청 과정에서 조건을 판정하고 최종 확인 전에 할인된 금액을 보여준다. 할인율·대상 금액·기간 경계와 가격 계산은 Q01/Q02에 남긴다(P04·P08 / BR09).
- **효도·골프·트레킹은 공동 모집 상품**으로, **동일 상품·동일 출발일의 전체 신청 여행자 수가 3명 이상**이면 출발을 확정한다. 신청 건수·계정 수로 대신하지 않는다(B15·P05 / BR07~BR08). 과제 원문은 모든 상품에 3명 조건을 제시하지만, 이 파일에서는 사용자 확정에 따라 허니문을 아래의 2인 전용 예외로 구분한다.
- **허니문 출발 규칙 — 사용자 확정(2026-10-05):** 허니문은 커플별 **정확히 2명의 전용 여행**으로 출발한다(BR13). 다른 커플의 신청 인원과 합산하지 않고 공동 모집의 3명 조건을 적용하지 않는다. 2인 출발 조건은 확정 규칙이며, 신청 저장 직후 자동 확정하는지 등의 세부 처리 시점까지 사용자 확정으로 단정하지 않는다. Q04의 출발 인원·공동 모집 제외 규칙은 해결되었으며, 신청 입력 항목은 Q03, 확정·문자의 세부 처리 시점은 Q07에서 보완한다.
- 출발 확정 시 문자를 요청한다. 허니문도 2인 전용 여행의 출발이 확정되면 문자를 요청한다(F13·P16 / BR10). **검토 반영(2026-10-05):** 새 출발 확정 시 해당 일정의 신청 고객들의 회원 연락처로 문자를 요청한다. 이미 확정된 일정의 추가 신청이 허용되어 저장되면 새 신청 고객에게만 문자를 요청한다. 문자 발송 실패로 저장된 신청과 출발 확정 상태를 취소하지 않는다. 허니문 확정·발송의 세부 시점, 추가 신청 허용 범위, 재시도 횟수·간격과 결과 불명 처리는 Q07에 남긴다.
- 고객 로그인 성공 직후 이전 여행을 팝업으로 보여준다. 최근 순이며 상품·기간·투어 등급·가격을 포함한다(F08~F10 / BR11~BR12). **검토 반영(2026-10-05):** 이력이 없으면 없다는 팝업으로 안내한다. 이력 범위·정렬 날짜·조회 실패와 가격 의미는 Q09/Q02에서 정한다.
- **다인 신청 — 검토 반영(2026-10-05):** 한 신청에 여러 여행자를 등록할 수 있다. 신청자는 로그인한 고객이며 실제 여행자 명단은 별도로 입력한다. 신청자가 여행에 참가하면 여행자 명단에도 포함한다. 출발 인원은 실제 등록된 여행자 수로 집계하며, 허니문 명단은 정확히 2명이다. 여행자별 상세 입력 항목은 Q03에서 정한다.
- **상품 수정 제한 — 사용자 확정(2026-10-05):** 해당 상품에 고객의 여행 신청이 한 건이라도 등록되어 있으면 상품 정보를 수정할 수 없다. MWT-UC7에서 신청 여부를 확인하고, 신청이 있으면 변경 내용을 저장하지 않는다. Q11의 신청된 상품 수정 허용 여부는 이 규칙으로 해소했다.

### 회원 유형과 권한 규칙

**사용자 확정(2026-10-05):** 회원가입 시 고객은 고객 유형을, 직원은 직원 유형을 선택한다. 시스템은 계정과 가입 정보, 선택한 유형에 맞는 역할을 저장한다. 고객 계정으로 로그인하면 고객 기능을, 직원 계정으로 로그인하면 상품 등록·수정 및 기념품 입고 기능을 이용한다.

직원 유형은 실제 직원이 선택하는 것으로 가정하며, 직원 자격 확인은 시스템 밖 회사 운영 사항으로 둔다.

## 2. 액터와 유스케이스 구성

### 액터와 관계의 모델링 초안

- **사용자:** 가입·로그인에 참여하는 고객·직원의 공통 역할. 고객과 직원은 이 역할을 특수화한다.
- **고객:** 여행 이력 확인, 상품 선택·구성, 신청.
- **직원:** 직원 유형으로 회원가입하고 직원 계정으로 로그인하여 상품 등록·수정 및 기념품 입고 기능을 이용한다.
- **음성인식 서비스·문자발송 서비스:** 기존 계획서의 외부 API에 해당하는 보조 액터. 내부 DB·시스템 자체는 외부 액터가 아니다.

팀원 문서의 **MWT-UC3이 MWT-UC2를 `extend`하는 모델링안**을 반영했다. 기본 MWT-UC2는 고객·직원의 인증과 역할별 접근으로 완결된다. 확장 지점은 **고객 인증 성공 후**, 조건은 **인증된 역할이 고객**이다. 이력 존재 여부는 조건이 아니므로 이력이 없어도 MWT-UC3 흐름을 실행한다.

현재 구성에는 별도 `include`를 두지 않는다. 로그인 완료·상품 구성 완료는 사전조건으로 사용한다. 음성 입력과 옵션 변경은 MWT-UC4의 같은 목표 안에서 처리하고, 할인·출발 확정·문자는 MWT-UC5에 담는다. 이 관계는 작성용 모델링 초안이며 전체 그림에도 같은 방향·조건을 반영해야 한다. 실제 StarUML 모델을 검증했다는 의미는 아니다.

### 유스케이스 명칭 표기 기준

MWT-UC3~MWT-UC5의 영문 이름은 사용자 요청(2026-10-05)에 따라 팀원 초안의 표기로 통일했다.

문서 변경 이력과 유스케이스도의 기능명은 아래 표의 **영문명**으로 통일한다. 유스케이스 설명서의 절 제목과 유스케이스 이름은 **한글명(영문명)**으로 병기하고, 흐름과 시나리오 본문은 한글로 작성한다. 예를 들어 설명서에는 `여행 신청(Submit Travel Application)`, 변경 이력과 그림에는 `Submit Travel Application`을 쓴다. 유스케이스 ID는 **MWT-UC1~MWT-UC8**로 표기한다. `MWT`는 Mister World Tour의 약자이며 번호 앞에 0을 붙이지 않는다. ID와 영문 철자는 모든 산출물에서 동일하게 유지한다. 시나리오 ID는 `MWT-UC1-S01`처럼 해당 유스케이스 ID를 앞에 붙인다. **참고 유즈케이스** 항목은 영문명을 생략하고 `로그인(MWT-UC2)`처럼 **한글명(ID)**으로 표기한다.

## 3. 유스케이스 설명서와 시나리오

각 유스케이스는 원본 분석산출물 양식의 11개 항목에 맞춰 작성한다. 주 흐름은 고객·직원의 요청과 입력을 액터 열에, 화면 표시·검증·저장·결과 안내를 MWT 열에 구분하여 적는다. 단계 번호는 두 열을 합친 실행 순서이며 시스템 처리는 연속될 수 있다. `—`는 해당 단계에서 별도의 행동이 없음을 뜻한다. 부 흐름 번호는 분기하는 주 흐름 단계에 맞춘다. 부 흐름과 제약 사항 뒤에 해당 시나리오를 배치한다. 요약에는 기능의 목적을 간단히 적고, 요구 연결과 확인 질문은 설명 표 아래에 기록한다. 사전·사후 조건은 짧은 상태 문장으로 번호를 붙이며, 사후 조건에는 성공 흐름의 결과를 적는다. 부 흐름은 필요한 분기별 처리 절차를 짧게 적고, 제약 사항에는 해당 기능에 적용되는 업무 규칙과 품질 목표를 적으며, 별도로 지정된 내용이 없으면 `없음.`으로 표기한다. 상세 정책과 모델링 설명은 5절의 세부 검토 메모에 기록한다.

#### MWT-UC1 회원가입(Sign Up)

**부 흐름 세부 기록**

**4a 입력 오류·계정 중복:** 수정할 항목을 안내하고 3단계로 돌아간다.

**5a 저장 실패:** 완료로 안내하지 않고 종료하거나 저장 여부 확인 후 재시도한다.

**정책과 모델링 검토 기록**

고객과 직원은 공통 회원가입 흐름에서 각자의 회원 유형을 선택한다. 시스템은 선택한 유형에 맞는 역할을 계정과 함께 저장한다. 직원 유형은 실제 직원이 선택하는 것으로 가정하며, 직원 자격 확인은 시스템 밖 운영 사항으로 둔다. 계정 식별자·인증 정보·검증 방식은 Q10에서 정한다. 입력 검증·오류 안내·복구 단계는 공통 처리 제안을 따른다. 저장 요청 후 결과가 불명확한 상황을 확인된 저장 실패와 구분하고, 재등록 전 결과 확인·중복 방지를 제안한다. 검증 실패 시 계정을 등록하지 않으며, 저장 결과가 불명확하면 확인 전 성공·실패를 단정하지 않는다.

#### MWT-UC2 로그인(Log In)

**부 흐름 세부 기록**

**2a 인증 실패:** 보호된 기능에 접근시키지 않고 1단계 재입력으로 돌아간다.

**4a 직원 로그인:** 고객 이력 팝업을 실행하지 않고 직원 기능 접근으로 완료한다.

**정책과 모델링 검토 기록**

기본 로그인은 고객·직원의 인증과 역할별 접근으로 완결된다. MWT-UC3 → MWT-UC2의 관계는 `extend`이며, 확장 지점은 고객 인증 성공 후, 확장 조건은 고객 역할의 인증 성공이다. 이력 존재 여부는 확장 조건이 아니므로 이력이 없어도 MWT-UC3을 실행한다. 현재 구성에는 별도 `include`를 두지 않는다. 직원 계정은 가입 완료 후 직원 업무 권한을 갖는다. 인증 실패 시 비인증 상태를 유지한다. 이력 조회 실패는 MWT-UC3의 부 흐름에서 다루며 인증 실패와 구분한다.

#### MWT-UC3 이전 여행 이력 확인(View Previous Travel History)

**부 흐름 세부 기록**

**1a 이력 없음:** 이전 여행이 없다는 팝업으로 안내하고 5단계로 이어진다.

**1b 조회 실패:** 빈 목록과 구분하여 오류를 안내한다. 재조회하면 1단계로 돌아가며 로그인 접근 유지 정책은 Q09에 남긴다.

**정책과 모델링 검토 기록**

MWT-UC2의 고객 인증 성공 후 확장 지점을 사용하며, 별도 메뉴 클릭을 필수 조건으로 두지 않는다. 이력 없음도 조회 실행 대상이다. 팝업 이력 범위를 단골 판정의 완료 여행 범위와 같다고 가정하지 않는다. 이력 없음 팝업은 이번 비교 검토에서 채택했다. 표시 대상 범위·정렬 날짜·조회 실패 처리는 Q09, 가격 표시의 의미는 Q02에서 정한다. NFR01에 따라 동일 PC에서 이력 조회를 10회 측정했을 때 평균 2초 이내를 목표로 한다.

#### MWT-UC4 여행 상품 선택 및 구성(Select and Configure Travel Product)

**부 흐름 세부 기록**

**음성 조회·선택 처리:** 주 흐름 1단계에서 음성 방식을 선택한 고객의 조회 명령은 4~5단계, 선택 명령은 8~9단계에서 인식 서비스로 전달하고 결과를 받는다. MWT는 GUI와 같은 구성 제한을 적용하고 결과를 화면에 표시한다. 음성 명령의 확인 후 반영 방식은 Q08에서 정한다.

**4a·8a 인식·연동 실패:** 실패를 기록하고 재시도 기능을 제공한다. 조회 명령은 3단계, 선택 명령은 7단계에서 다시 입력한다. GUI 방식으로 전환하려면 1단계로 돌아가 방식을 다시 선택한다. 재시도 횟수와 처리 방식은 Q08에서 정한다.

**4b·8b 모호한·지원하지 않는 명령:** 임의 조회·선택을 피하고 조회 명령은 3단계, 선택 명령은 7단계에서 재입력·추가 선택을 요청하는 안을 제안한다.

**6a 상품 없음·조회 실패:** 두 결과를 구분하여 안내하고 종료하거나 3단계에서 재조회한다.

**10a 허니문·효도 클래식 요청:** 제한을 안내하고 7단계의 허용 등급 선택으로 돌아간다.

**11a 기본 구성 유지:** 변경 없이 12~13단계로 이어진다.

**12a 허용되지 않는 조합:** 11단계 재선택으로 돌아간다. 허니문·효도 호텔 하향은 Q05 결정 전 결과를 단정하지 않는다.

**12b 프리미엄 샴페인 추가:** Q06에 따라 기본 포함분·추가량·추가금을 구분하여 12단계 결과 표시로 이어진다.

**12c 변경 처리 실패:** 오류를 안내하고 직전 유효 구성을 유지하는 안을 제안한다.

**정책과 모델링 검토 기록**

GUI와 음성은 같은 목표의 대안 경로다. 사용자 요청(2026-10-06)에 따라 1단계에서 조회·선택 방식을 고르고, 고객·MWT·음성인식 서비스의 동작을 세 열로 구분한다. GUI 방식은 4~5단계와 8~9단계를 건너뛴다. 옵션 변경도 MWT-UC4 내부 단계이며 화면에서 진행한다. 클래식 트레킹의 고급 식사·샴페인은 허용한다. 음성 옵션 변경·음성 신청까지 지원한다고 확대 해석하지 않는다. 비회원 조회 허용은 검토 사항이다. 신청 정보 저장은 MWT-UC5에서 수행한다. 실패·모호한 음성으로 기존 선택을 덮어쓰지 않는 안을 검토한다.

#### MWT-UC5 여행 신청(Submit Travel Application)

**부 흐름 세부 기록**

**4a 입력·구성 오류:** 3단계 보완 입력 또는 MWT-UC4 재선택으로 돌아간다.

**4b 이미 확정된 일정의 신청:** Q07에서 정한 추가 신청 허용 정책에 따라 5~8단계로 진행하거나 저장 전에 중단한다. 허용 여부 자체는 아직 미정이다.

**4h 허니문 2인 전용 여행:** 해당 커플의 정확히 2인 전용 여행으로 처리한다. 5~8단계의 가격·할인·신청 확인·저장은 공통으로 수행한다. 공동 모집 9~10단계의 인원 합산과 3명 조건을 적용하지 않고 허니문의 2인 출발 규칙에 따라 출발 상태를 처리한다. 출발이 확정되면 11단계 문자 요청을 수행하고, 12단계에서 결과를 표시한다. 신청 입력 항목은 Q03, 확정 처리의 세부 시점은 Q07에서 보완한다. 2명이 아닌 입력의 보완·저장 처리도 신청 방식에 맞춰 정한다.

**5a 단골 조건 미충족:** 단골 할인 없는 가격으로 6단계에 이어진다.

**5b 가격·할인 계산 실패:** 임의 금액이나 할인 판정으로 저장하지 않고 오류를 안내하는 안을 제안한다.

**7a 등록 요청 반복:** 실제 추가 신청인지 기존 요청의 반복인지 확인하여 중복 집계·문자를 막는 안을 제안한다.

**8a 저장 실패:** 완료로 안내하지 않고 집계·출발 확정·문자를 진행하지 않는다. 결과 확인 후 재시도하는 안을 제안한다.

**10a 총인원 3명 미만:** 신청은 저장 성공, 출발은 미확정이다. 11단계 확정 문자를 건너뛰고 12단계로 이동한다. 허니문 2인 전용 신청을 공동 모집 인원 부족으로 처리하지 않는다.

**10b 이미 확정된 공동 모집 일정:** 추가 신청 허용 여부는 4단계에서 검사한다. 허용되어 저장된 경우 출발을 다시 확정하지 않고, 새 신청 고객만 대상으로 11단계의 문자 발송 절차를 수행한 뒤 12단계로 이동한다. 기존 신청 고객에게 다시 보내지 않는다. 추가 신청 허용 범위는 Q07에서 정한다.

**11a 문자 실패·결과 불명:** 신청·확정 상태를 유지하고 문자 발송 결과를 기록한 뒤 12단계에서 신청 결과와 알림 상태를 구분해 안내한다. 확인된 실패는 재시도한다. 횟수·간격은 Q07에서 정하며, 결과가 불명확하면 성공이나 실패를 단정하지 않고 발송 내역 확인·중복 방지를 검토한다. 이 흐름은 새 출발 확정과 10b의 새 신청 고객 통지 모두에 적용한다.

**정책과 모델링 검토 기록**

MWT-UC2 로그인과 MWT-UC4 구성 완료는 사전조건이다. 이력 팝업과 별개로 완료 여행 정보를 사용해 단골을 판정한다. 할인된 금액은 최종 신청 확인 전에 표시한다. 할인율·대상 금액·기간 경계는 Q01에서 정한다. 결제 완료를 신청 조건으로 추가하지 않는다. 옵션 변경은 필수가 아니다. 문자 실패와 신청 저장 실패를 구분하며, 문자 실패로 저장된 신청과 확정 상태를 취소하지 않는다.

#### MWT-UC6 여행 상품 등록(Register Tour Product)

**부 흐름 세부 기록**

**4a 입력 오류·구성 제한 위반:** 시스템이 수정할 항목을 안내하고 직원은 주 흐름 3단계로 돌아가 수정한다. 입력 누락·잘못된 가격/일정과 허니문·효도 초기 클래식 제공 등 구성 규칙 위반을 포함한다.

**5a 저장 실패:** 시스템이 완료로 안내하지 않으며, 저장 결과를 확인한 후 재시도하거나 종료한다.

**정책과 모델링 검토 기록**

테마·등급·옵션 구성은 공통 상품 구성 규칙(BR01~BR06)을 따른다. 허니문·효도의 초기 투어 등급은 그랜드 이상이다. 전체 등록 필드, 공개 시점·상태는 Q11에서 정하며 가격 계산·호텔 하향·샴페인 세부 정책은 Q02·Q05·Q06에 남긴다. 불완전한 상품을 노출하지 않는 처리는 제안이다. 현실의 상품 기획과 기획 내용을 시스템에 입력·등록하는 동작을 구분하되, 기획 지원 입력 기능을 제외한다는 뜻은 아니다.

#### MWT-UC7 여행 상품 수정(Modify Tour Product)

**부 흐름 세부 기록**

**2a 상품 없음·조회 실패:** 등록된 상품이 없으면 시스템이 안내하고 종료한다. 조회에 실패하면 오류를 안내하고 직원은 재조회하거나 종료한다.

**4a 선택 상품을 찾을 수 없음:** 시스템이 안내하고 주 흐름 2단계로 돌아가 목록을 다시 보여준다. 직원은 3단계에서 수정할 상품을 다시 선택한다.

**6a 입력 오류·상품 규칙 위반:** 수정한 상품 정보에 오류가 있거나 상품 규칙을 위반하면 시스템이 수정할 항목을 안내한다. 직원은 주 흐름 5단계로 돌아가 정보를 수정한다. 허니문·효도 상품의 초기 투어 등급을 클래식으로 바꾸는 경우도 포함한다.

**6b 신청이 있는 상품:** 해당 상품에 고객의 여행 신청이 한 건이라도 등록되어 있으면 시스템이 수정할 수 없음을 안내한다. 변경 내용을 저장하지 않고 기존 상품 정보를 유지한 채 주 흐름 2단계로 돌아간다. 직원은 3단계에서 다른 상품을 선택할 수 있다.

**7a 저장 실패:** 시스템이 수정 완료로 안내하지 않으며, 저장 결과를 확인한 후 재시도하거나 종료한다. 기존 유효 정보를 유지하는 안은 정책 검토 기록에 남긴다.

**정책과 모델링 검토 기록**

상품 수정의 기본 절차는 수정 기능 선택, 등록된 상품 목록 표시, 수정 대상 선택, 기존 정보 표시, 직원의 수정·저장 요청, 시스템의 정보 검사·신청 여부 확인·저장·결과 안내다. 참고 유즈케이스에는 등록된 상품을 수정한다는 관계로 MWT-UC6만 남긴다. 신청이 있는 상품의 수정 제한은 6b에 반영한다.

변경 후에도 공통 상품 구성 규칙(BR01~BR06)을 충족해야 한다. 허니문·효도의 초기 투어 등급은 그랜드 이상이다. **사용자 확정(2026-10-05): 신청이 한 건이라도 등록된 상품은 수정할 수 없다.** 신청이 없는 상품의 수정 가능한 항목과 동시 수정 정책은 Q11에서 정한다. 기존 신청·과거 이력의 가격과 구성을 자동으로 바꾼다고 가정하지 않으며, 가격 계산·호텔 하향·샴페인 세부 정책은 Q02·Q05·Q06에 남긴다. 저장 실패 시 기존 유효 정보를 유지하는 처리는 제안이다. 수정 대상의 존재는 조회·선택 단계에서 확인한다.

#### MWT-UC8 기념품 입고 등록(Record Souvenir Stock Receipt)

**부 흐름 세부 기록**

**2a 재고 조회 실패:** 시스템이 현재 재고를 조회하지 못하면 오류를 안내한다. 직원은 재조회하거나 종료한다. 조회 실패를 재고 0으로 표시하지 않는다.

**4a 입력 오류:** 입고 수량이 비어 있거나 1 이상의 정수가 아니면 시스템이 오류를 안내한다. 0·음수·소수·문자 입력은 저장하지 않으며 재고도 변경하지 않는다. 직원은 주 흐름 3단계로 돌아가 수량을 다시 입력한다.

**5a 입고 반영 실패:** 시스템이 완료로 안내하지 않는다. 입고 내역의 저장 여부와 재고 반영 여부를 확인한 후 재시도하거나 종료한다. 부분 반영·재시도로 인한 수량 중복을 막는 상세 처리는 Q12에서 보완한다.

**정책과 모델링 검토 기록**

**사용자 확정(2026-10-05):** 기념품 목록을 미리 등록한다. 품목의 종류와 개수는 이 설명서에서 지정하지 않는다. 입고 입력 화면에서 이 목록과 물품별 현재 재고를 보여주며, 재고가 없는 물품도 목록에 표시하고 수량은 0개로 보여준다. 직원은 목록에서 입고할 기념품을 선택하고 수량을 입력한다. 유효한 입고 요청은 입고 내역을 저장하고 해당 물품의 현재 재고에 입고 수량을 더한다. 처리 후 입고 결과와 변경된 재고를 표시한다. MWT-UC8-S01은 재고 0개인 골프공을 5개 입고했을 때 5개가 되는 예시이며 실제 시험 통과 기록은 아니다.

**사용자 확정(2026-10-05):** 입고 수량은 1 이상의 정수만 허용한다. 품목 추가 기능은 UC8에 포함하지 않는다. 부분 반영·수량 중복 방지의 상세 처리와 출고·자동 차감의 추가 범위는 Q12에서 검토한다. 음수 입고로 출고를 대신 처리하지 않는다.
