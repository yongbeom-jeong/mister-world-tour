# 미스터 월드 유스케이스 설명과 시나리오 초안

작성일: 2026-10-03  
수정 내용: 상품 선택과 옵션 변경을 UC04로 통합하고, 팀원 설명서의 간결한 형식과 관계 설명을 반영했다.

고객과 직원의 목표를 8개 유스케이스로 정리한다. 본문에는 기본·대안 흐름을, 뒤에는 시나리오와 미정 질문을 모았다. 팀원은 맡은 설명과 질문 처리안을 보완하고 같은 ID로 시퀀스도를 작성한다. 업무 정책의 팀 합의가 끝난 문서는 아니다.

### 신청과 이력 규칙

- 단골은 **최근 3년 이내 여행을 3회 이상 완료한 고객**이다. 할인율·대상·시점·가격 계산은 Q01/Q02에 남긴다(P04·P08 / BR09).
- 과제 원문은 **각 상품의 신청 인원 3명 이상** 출발 확정이다. 계획서는 **동일 상품·동일 출발일의 전체 신청 여행자 수**를 집계한다. 신청 건수·계정 수로 대신하지 않는다(B15·P05 / BR07~BR08).
- **허니문 해석안:** 정확히 두 명이 떠나는 전용 여행으로 보고 공동 모집에서 제외하자는 사용자 제안이다(BR13). 이 안을 채택하면 효도·골프·트레킹만 공동 모집으로 처리한다. 원문에 예외가 명시되지 않아 Q04는 계속 열어둔다. 두 명 신청 즉시 확정으로 추가 단정하지 않는다.
- 출발 확정 시 문자를 요청한다. 허니문도 확정 문자 요구를 유지한다. 수신자·추가 신청·재시도 상세는 Q04/Q07에 남긴다(F13·P16 / BR10).
- 고객 로그인 성공 직후 이전 여행을 팝업으로 보여준다. 최근 순이며 상품·기간·투어 등급·가격을 포함한다. 이력 범위·정렬 날짜·빈 목록·가격 의미는 Q09/Q02에서 정한다(F08~F10 / BR11~BR12).

### 공통 처리 제안

## 2. 액터와 유스케이스 구성

### 액터와 관계의 모델링 초안

- **사용자:** 가입·로그인에 참여하는 고객·직원의 공통 역할. 고객과 직원은 이 역할을 특수화한다.
- **고객:** 여행 이력 확인, 상품 선택·구성, 신청.
- **직원:** 상품 등록·수정, 기념품 입고. 직원 가입과 권한 부여는 구분한다.
- **음성인식 서비스·문자발송 서비스:** 기존 계획서의 외부 API에 해당하는 보조 액터. 내부 DB·시스템 자체는 외부 액터가 아니다.

팀원 문서의 **UC03이 UC02를 `extend`하는 모델링안**을 반영했다. 기본 UC02는 고객·직원의 인증과 역할별 접근으로 완결된다. 확장 지점은 **고객 인증 성공 후**, 조건은 **인증된 역할이 고객**이다. 이력 존재 여부는 조건이 아니므로 이력이 없어도 UC03 흐름을 실행한다.

현재 구성에는 별도 `include`를 두지 않는다. 로그인 완료·상품 구성 완료는 사전조건으로 사용한다. 음성 입력과 옵션 변경은 UC04의 같은 목표 안에서 처리하고, 할인·출발 확정·문자는 UC05에 담는다. 이 관계는 작성용 모델링 초안이며 전체 그림에도 같은 방향·조건을 반영해야 한다. 실제 StarUML 모델을 검증했다는 의미는 아니다.

## 3. 유스케이스 설명

### UC01 회원가입

**주요 액터:** 고객·직원  
**목표:** 서비스 이용을 위한 계정과 가입 정보를 등록한다.  
**사전조건:** 가입 기능에 접근할 수 있다. 직원 가입 경로·자격 확인은 Q10에서 정한다.  
**시작 사건:** 사용자가 회원가입을 선택한다.  
**관련 요구·참고:** FR03~FR07, P02 / UC02 / Q10

#### 기본 흐름

1. 사용자가 회원가입을 선택한다.
2. 시스템이 계정 정보와 성명·주소·연락처 입력을 요청한다.
3. 사용자가 정보를 입력하고 등록을 요청한다.
4. 시스템이 입력값과 계정 식별 정보의 중복을 검사한다.
5. 유효한 계정과 가입 정보를 저장한다.
6. 시스템이 가입 결과를 안내한다.

#### 대안과 예외 흐름

- **4a 입력 오류·계정 중복:** 수정할 항목을 안내하고 3단계로 돌아간다.
- **5a 저장 실패:** 완료로 안내하지 않고 종료하거나 저장 여부 확인 후 재시도한다.
- **직원 가입:** 직원 정보 등록과 업무 권한 활성화를 구분한다. 부여·승인 절차는 Q10에 따라 보완하며 가입만으로 권한을 확정하지 않는다.

**사후조건:** 계정과 성명·주소·연락처가 저장된다. 검증 실패 시 등록하지 않는다. 저장 결과가 불명확하면 확인 전 성공·실패를 단정하지 않는다. 직원 권한은 별도 결정 결과에 따른다.

### UC02 로그인

**주요 액터:** 고객·직원  
**목표:** 인증을 받아 역할에 맞는 기능을 이용한다.  
**사전조건:** 등록된 계정이 있다.  
**시작 사건:** 사용자가 로그인을 요청한다.  
**관련 요구·참고:** FR01~FR02, FR08~FR10, P02 / UC01·UC03 / Q10·Q09

#### 기본 흐름

1. 사용자가 계정 인증 정보를 입력한다.
2. 시스템이 계정을 인증한다.
3. 시스템이 고객·직원 역할과 접근 권한을 확인한다.
4. 인증된 역할에 맞는 기능 접근을 제공한다. 고객 인증 성공 후 확장 지점에서 UC03을 시작한다.

#### 대안과 예외 흐름

- **2a 인증 실패:** 보호된 기능에 접근시키지 않고 1단계 재입력으로 돌아간다.
- **3a 직원 권한 미확정:** 직원 업무 접근을 허용하지 않는 안을 검토한다. 대기 안내·다른 역할 접근은 Q10에서 정한다.
- **4a 직원 로그인:** 고객 이력 팝업을 실행하지 않고 직원 기능 접근으로 완료한다.
- **4b 고객 이력 조회 실패:** UC03 오류 흐름으로 이어진다. 인증 성공과 이력 조회 실패를 구분하고 접근 유지·재조회 정책을 Q09에서 정한다.

**사후조건:** 인증 상태와 확인된 역할의 접근이 제공된다. 인증 실패 시 비인증 상태를 유지한다. UC03의 실패만으로 인증 실패를 선언하지 않는다.  
**관계:** UC03 → UC02 `extend`, 확장 지점 고객 인증 성공 후, 확장 조건 고객 역할의 인증 성공.

### UC03 이전 여행 이력 확인

**주요 액터:** 고객  
**목표:** 로그인 직후 저장된 이전 여행 정보를 확인한다.  
**사전조건:** 고객 인증이 성공했다.  
**시작 사건:** UC02의 고객 인증 성공. 메뉴 클릭을 필수 조건으로 두지 않는다.  
**관련 요구·참고:** FR25~FR30, BR11~BR12, NFR01 / UC02·UC05·UC06·UC07 / Q09·Q02

#### 기본 흐름

1. 시스템이 로그인한 고객의 표시 대상 여행 이력을 조회한다.
2. 상품·기간·투어 등급·가격을 가져온다.
3. Q09에서 정할 날짜 기준으로 최근 순 정렬한다.
4. 시스템이 정렬된 목록을 팝업으로 표시한다.
5. 고객이 이력을 확인하고 다음 기능으로 이동한다.

#### 대안과 예외 흐름

- **1a 이력 없음:** 이전 여행이 없다는 팝업 안내 후 5단계로 이어지는 안을 제안한다.
- **1b 조회 실패:** 빈 목록과 구분하여 오류를 안내한다. 재조회하면 1단계로 돌아가며 로그인 접근 유지 정책은 Q09에 남긴다.
- **3a 같은 날짜의 이력:** Q09의 추가 정렬 기준에 따라 4단계로 이어진다.

**사후조건:** 이력 목록 또는 빈 목록 안내가 표시된다. 조회로 기존 여행 정보는 바뀌지 않는다. 오류 안내 방식은 제안이다.  
**관계·업무 규칙:** UC02의 확장 지점을 사용한다. 이력 없음도 조회 실행 대상이다. 팝업 이력 범위를 단골 판정의 완료 여행 범위와 같다고 가정하지 않는다.

### UC04 여행 상품 선택 및 구성

**주요 액터:** 고객 / **보조 액터:** 음성인식 서비스  
**목표:** 원하는 여행 상품·투어 등급과 세부 구성을 정한다.  
**사전조건:** 계획서 이용 흐름에 따라 고객 로그인 완료를 기본으로 한다. 비회원 조회 허용은 검토 사항이다.  
**시작 사건:** 고객이 상품 조회·선택을 시작한다.  
**관련 요구·참고:** FR01, FR11~FR19, FR35~FR36, BR01~BR06, NFR01~NFR02 / UC05·UC06·UC07 / Q02·Q05·Q06·Q08

#### 기본 흐름

1. 고객이 GUI로 여행 상품 목록을 요청한다.
2. 시스템이 등록 상품과 테마를 제시한다.
3. 고객이 상품·테마·투어 등급을 선택한다.
4. 시스템이 허니문·효도 그랜드 이상 제한을 검사하고 테마·등급별 기본 구성을 보여준다.
5. 고객은 필요하면 호텔·교통·식사를 개별 변경하거나 음료를 추가한다. 기본 구성 그대로 진행할 수도 있다.
6. 시스템이 변경 조합을 검증하고 최종 구성·가격을 보여준다. 선택지·가격 계산은 Q02/Q05/Q06에 따른다.
7. 고객이 구성을 확인하여 신청에 사용할 선택을 완료한다.

#### 대안과 예외 흐름

- **1a 음성 조회·선택:** 시스템이 음성인식 서비스에 인식을 요청하고 결과를 받아 지원 명령에 맞게 조회·선택한다. GUI와 같은 구성 제한을 적용하고 결과를 화면에 표시한다. 확인 후 반영 방식은 Q08에서 정한다.
- **1b 인식·연동 실패:** 실패를 기록하고 재시도 기능을 제공한다. 재입력 또는 GUI 사용으로 복귀하는 상세 안은 Q08에서 정한다.
- **1c 모호한·지원하지 않는 명령:** 임의 선택을 피하고 재입력·추가 선택을 요청하는 안을 제안한다.
- **2a 상품 없음·조회 실패:** 두 결과를 구분하여 안내하고 종료하거나 재조회한다.
- **4a 허니문·효도 클래식 요청:** 제한을 안내하고 3단계의 허용 등급 선택으로 돌아간다.
- **5a 기본 구성 유지:** 변경 없이 6~7단계로 이어진다.
- **6a 허용되지 않는 조합:** 5단계 재선택으로 돌아간다. 허니문·효도 호텔 하향은 Q05 결정 전 결과를 단정하지 않는다.
- **6b 프리미엄 샴페인 추가:** Q06에 따라 기본 포함분·추가량·추가금을 구분하여 6단계 결과 표시로 이어진다.
- **6c 변경 처리 실패:** 오류를 안내하고 직전 유효 구성을 유지하는 안을 제안한다.

**사후조건:** 유효한 상품·등급·구성이 정해진다. 신청 저장은 UC05에서 수행한다. 실패·모호한 음성으로 기존 선택을 덮어쓰지 않는 안을 검토한다.  
**관계·업무 규칙:** GUI와 음성은 같은 목표의 대안 경로이며 옵션 변경도 UC04 내부 단계다. 클래식 트레킹의 고급 식사·샴페인은 허용한다. 음성 옵션 변경·음성 신청까지 지원한다고 확대 해석하지 않는다.

### UC05 여행 신청

**주요 액터:** 고객 / **보조 액터:** 문자발송 서비스  
**목표:** 선택한 여행을 신청하고 출발 상태를 확인한다.  
**사전조건:** 고객 로그인 및 UC04의 유효한 구성 완료. 옵션 변경은 필수가 아니다.  
**시작 사건:** 고객이 여행 신청을 시작한다.  
**관련 요구·참고:** FR20~FR24, FR35~FR36, BR07~BR10, BR13(제안), VAL03 / UC03·UC04·UC06·UC07 / Q01~Q04·Q07

#### 기본 흐름

허니문 전용 해석안을 채택할 경우 아래는 효도·골프·트레킹의 공동 모집 흐름이며 허니문은 3h로 구분한다.

1. 시스템이 UC04의 상품·구성을 보여주고 출발일·신청 여행자 수/정보 입력을 요청한다.
2. 고객이 출발일과 신청 정보를 입력한다. 다인 신청·동반자 항목은 Q03에서 정한다.
3. 시스템이 입력과 구성의 유효성을 확인한다. 이미 확정된 일정은 저장 전에 Q07의 추가 신청 허용 정책도 확인한다.
4. 시스템이 가격을 계산하고 최근 3년 이내 완료 여행 3회 이상이면 단골 할인을 적용한다. 가격 단위·계산식·할인율·대상·시점은 Q01/Q02에 따른다.
5. 시스템이 최종 내용·금액을 보여주고 고객이 확인하여 신청 등록을 요청한다.
6. 시스템이 신청 정보를 저장한다.
7. 시스템이 동일 상품·동일 출발일의 전체 신청 여행자 수를 집계한다.
8. 총인원이 3명 이상이고 아직 미확정이면 새로 출발을 확정한다.
9. 새로 확정된 출발의 문자 안내를 외부 서비스에 요청하고 결과를 기록한다. 수신자·발송 단위는 Q07에서 정한다.
10. 시스템이 신청 결과와 출발 상태를 표시한다.

#### 대안과 예외 흐름

- **3a 입력·구성 오류:** 2단계 보완 입력 또는 UC04 재선택으로 돌아간다.
- **3b 이미 확정된 일정의 신청:** Q07에서 정한 추가 신청 허용 정책에 따라 4~6단계로 진행하거나 저장 전에 중단한다. 허용 여부 자체는 아직 미정이다.
- **3h 허니문 전용 여행 제안:** 정확히 두 명의 전용 여행으로 처리하고 다른 커플과 인원을 합쳐 3명을 기다리지 않는 안이다. 4~6단계 가격·할인·저장은 공통으로 수행한다. 공동 모집 7~8단계 대신 Q03/Q04에서 정할 전용 신청 단위·출발 확정 조건으로 처리하고, 확정 시 9단계 문자 요구를 유지한다. 두 명 신청만으로 즉시 확정된다고 단정하지 않는다.
- **4a 단골 조건 미충족:** 단골 할인 없는 가격으로 5단계에 이어진다.
- **4b 가격·할인 계산 실패:** 임의 금액이나 할인 판정으로 저장하지 않고 오류를 안내하는 안을 제안한다.
- **6a 저장 실패:** 완료로 안내하지 않고 집계·출발 확정·문자를 진행하지 않는다. 결과 확인 후 재시도하는 안을 제안한다.
- **8a 총인원 3명 미만:** 신청은 저장 성공, 출발은 미확정이다. 9단계 확정 문자를 건너뛰고 10단계로 이동한다. 허니문 제안 분기를 인원 부족으로 처리하지 않는다.
- **8b 이미 확정된 공동 모집 일정:** 추가 신청 허용 여부는 3단계에서 검사하며 새 확정 처리를 반복하지 않는다. 신규 신청자 통지·기존 고객 재발송 정책은 Q07에 따라 처리하고 10단계로 이동한다.
- **9a 문자 실패·결과 불명:** 실패 기록·재시도 방향을 유지한다. 신청·확정 상태를 유지하며 알림 실패를 구분해 10단계로 가는 안은 제안으로 검토한다.
- **5a 등록 요청 반복:** 실제 추가 신청인지 기존 요청의 반복인지 확인하여 중복 집계·문자를 막는 안을 제안한다.

**사후조건:** 신청이 저장된다. 공동 모집 인원이 반영되고 새로 조건을 충족하면 확정·문자 요청을 수행한다. 3명 미만도 신청 성공이다. 허니문 확정 결과는 Q04에 따라 보완한다. 문자 실패와 신청 저장 실패를 구분한다.  
**관계·업무 규칙:** UC02 로그인과 UC04 구성 완료는 사전조건이다. 이력 팝업과 별개로 완료 여행 정보를 사용해 단골을 판정한다. 가격·할인 단계의 위치는 Q01의 적용 시점 결정 후 조정한다. 결제 완료를 신청 조건으로 추가하지 않는다.

### UC06 여행 상품 등록

**주요 액터:** 직원  
**목표:** 기획한 상품의 정보·가격·구성을 시스템에 등록한다.  
**사전조건:** 직원 로그인 및 상품 업무 권한.  
**시작 사건:** 직원이 새 상품 등록을 선택한다.  
**관련 요구·참고:** FR02, FR31, P06, BR01~BR06 / UC04·UC05·UC07 / Q11·Q02·Q05·Q06

#### 기본 흐름

1. 직원이 상품 등록 기능을 연다.
2. 시스템이 정보·가격·구성 입력 항목을 제시한다.
3. 직원이 기획한 상품 정보·테마·등급·서비스 구성·가격·여행 기간·출발일 등을 입력한다. 전체 필드는 Q11에서 정한다.
4. 시스템이 필수값·가격·일정과 테마·등급·옵션 규칙을 검사한다.
5. 직원이 등록을 요청하고 시스템이 유효한 상품 정보를 저장한다.
6. 시스템이 등록 결과를 안내한다.

#### 대안과 예외 흐름

- **4a 입력 누락·잘못된 가격/일정:** 보완할 항목을 안내하고 3단계로 돌아간다.
- **4b 기본 구성·등급 제한 위반:** 허니문·효도 초기 클래식 제공 등 규칙 위반을 수정한다.
- **5a 저장 실패:** 완료로 안내하지 않고 결과 확인 후 재시도하거나 종료한다.

**사후조건:** 기획한 상품 정보·가격·구성이 등록된다. 공개 시점·상태는 Q11에서 정한다. 불완전한 상품을 노출하지 않는 처리는 제안이다.  
**업무 범위:** 현실의 상품 기획과 기획 내용을 시스템에 입력·등록하는 동작을 구분한다. 기획 지원 입력 기능을 제외한다는 뜻은 아니다.

### UC07 여행 상품 수정

**주요 액터:** 직원  
**목표:** 등록된 상품의 정보·가격·구성을 갱신한다.  
**사전조건:** 직원 로그인 및 상품 업무 권한. 수정 대상의 존재는 조회·선택 단계에서 확인한다.  
**시작 사건:** 직원이 상품 수정을 시작한다.  
**관련 요구·참고:** FR02, FR32, P06, BR01~BR06 / UC03~UC06 / Q11·Q02·Q05·Q06

#### 기본 흐름

1. 직원이 등록된 상품을 조회한다.
2. 직원이 수정할 상품을 선택한다.
3. 시스템이 기존 정보·구성·가격·일정을 보여준다.
4. 직원이 허용된 항목을 수정한다.
5. 시스템이 변경값·기본 규칙과 기존 신청에 대한 영향을 확인한다.
6. 직원이 저장을 요청하고 시스템이 결정된 정책에 따라 변경 내용을 저장한다.
7. 시스템이 수정 결과를 안내한다.

#### 대안과 예외 흐름

- **1a 상품 없음·조회 실패:** 결과를 구분하여 안내하고 종료하거나 1단계 재조회로 돌아간다.
- **2a 선택 상품을 찾을 수 없음:** 1~2단계 조회·선택으로 돌아간다.
- **5a 잘못된 변경:** 수정할 항목을 안내하고 4단계로 돌아간다.
- **5b 이미 신청된 상품 변경:** Q11의 허용 범위·기존 신청 처리 정책에 따라 6단계로 이어지거나 변경을 중단한다.
- **6a 저장 실패:** 완료로 안내하지 않고 기존 유효 정보를 유지하는 안을 제안한다.

**사후조건:** 허용된 변경 사항이 저장된다. 기존 신청·과거 이력의 가격과 구성을 자동으로 바꾼다고 가정하지 않는다. 실패 시 정보 유지·동시 수정 정책은 제안 또는 미정이다.

### UC08 기념품 입고 등록

**주요 액터:** 직원  
**목표:** 기념품을 창고에 추가하고 입고 수량을 저장한다.  
**사전조건:** 직원 로그인 및 입고 업무 권한.  
**시작 사건:** 직원이 입고 등록을 선택한다.  
**관련 요구·참고:** FR02, FR33~FR34, P09 / UC02 / Q12

#### 기본 흐름

1. 직원이 입고 등록 기능을 연다.
2. 시스템이 물품·수량 입력을 요청한다.
3. 직원이 입고 물품과 수량을 입력한다. 대상 예시는 커플티·건강 인삼 기념품·골프공·스카프다.
4. 시스템이 입력값을 검증한다. 수량을 양의 정수로 제한하는 안을 제안한다.
5. 직원이 등록을 요청하고 시스템이 창고 추가·입고 수량을 저장한다.
6. 시스템이 입고 결과를 안내한다.

#### 대안과 예외 흐름

- **3a 신규 물품:** 같은 화면에서 물품도 추가할지 미리 등록된 물품만 선택할지 Q12에서 정한다. 미등록 물품을 일괄 거부한다고 확정하지 않는다.
- **4a 입력 오류:** 보완할 항목을 안내하고 3단계로 돌아간다. 0·음수·비정수 처리도 제안 수용 여부에 따른다.
- **5a 저장 실패:** 완료로 안내하지 않고 종료하거나 저장 여부 확인 후 재시도한다. 부분 저장·수량 중복을 막는 처리를 제안한다.
- **등록 후 오입력 발견:** 정정·수정 절차는 Q12 결정 후 보완하며 단순 재등록으로 대신하지 않는다.

**사후조건:** 물품 창고 추가와 입고 수량이 저장된다. 입고 내역·현재 재고 증가의 동시 반영은 Q12의 처리 제안이다. 출고·자동 차감·품목 관리의 추가 범위는 미정으로 남긴다.
