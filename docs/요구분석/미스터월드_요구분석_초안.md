### 허니문 출발 조건의 새 해석 제안

사용자는 허니문이 정확히 두 명만 떠나는 전용 여행이며 단체 공동 모집 대상이 아니라는 해석을 제시했다. 이 안에서는 **허니문은 2인 전용**, **효도·골프·트레킹은 동일 상품·동일 출발일의 전체 여행자 3명 이상 모집**으로 구분한다. 과제 안내의 B15는 모든 상품에 3명 조건을 제시하므로 원문과 제안을 구분한다. Q04는 종료하지 않고 예외 해석의 합의·확인, 전용 여행의 신청 단위·출발 확정 시점·문자 시점을 남긴다. 두 명 신청만으로 즉시 출발 확정된다고 추가로 단정하지 않는다.

### 이식한 모델링 초안: 8개 목표와 액터 관계

상품 조회·선택과 옵션 변경은 고객이 신청할 여행 구성을 정하는 하나의 목표로 묶어 **UC04 여행 상품 선택 및 구성**으로 통합한다. 옵션 변경은 선택사항이며, GUI와 음성은 같은 조회·선택 목표의 대안 경로이다. 기능 요구 ID와 미정 질문은 통합 과정에서 삭제하지 않는다. 공통 UC01~UC08의 요구 연결은 5절의 추적표를 따른다.

| 관계 | 모델링 초안 | 조건·주의 |
|---|---|---|
| 액터 일반화 | 고객·직원은 추상 액터 **사용자**의 특수화이다. 일반화 화살표는 사용자 쪽을 향한다. | 사용자는 공유 가입·로그인 역할을 표현하는 추상 액터이며, 새 관리자나 별도 권한 역할을 추가하는 것이 아니다. |
| 확장 | **UC03 이전 여행 이력 확인 → UC02 로그인**, `extend` | 확장 지점은 **고객 인증 성공 후**, 조건은 **고객 역할의 인증 성공**이다. 이력 존재가 조건이 아니므로 이력이 없는 고객도 조회 흐름을 실행한다. 빈 목록 표시 상세는 Q09에 남긴다. |
| 포함 | 현재 8개 목표에서 별도 `include` 관계를 두지 않는다. | 로그인과 앞선 상품 선택은 필요한 기능의 사전조건으로 표현한다. 선행 기능을 매번 다시 실행한다는 관계로 만들지 않는다. |

위 관계는 팀원 문서에서 이식한 모델링 초안이다. 고객 로그인 시 팝업이라는 확정 요구를 설명하는 방식이며, 팀 전체 합의나 StarUML 등 UML 도구에 이미 작성된 모델로 주장하지 않는다. 음성·문자 API는 외부 보조 액터 후보이고 내부 DB는 액터가 아니다.

고객 문서에 명시되지 않은 결제·취소·환불·상품 삭제·회원정보 수정·자동 재고 차감은 추가 범위 후보이다. 명시되지 않았다는 이유로 포함을 금지하거나 필수 기능으로 추가하지 않는다. 추가하려면 회의에서 근거·범위·일정 영향을 기록한다.

호텔 장식·안마·차량 운행 등은 시스템이 표현·구성할 여행 서비스 사양이다. 이 시스템이 현실의 서비스를 직접 수행하는 것으로 해석하지 않는다. 제목의 AI 표현에서 추천·챗봇·일정 생성 같은 새 기능을 도출하지 않는다.

### 일관성 검토 결과

1. **최소 인원 표현:** 과제 안내·계획서 원문은 **3명 이상**으로 유지한다. 새 해석 제안의 유스케이스 흐름에서는 효도·골프·트레킹의 공동 모집과 허니문 2인 전용 여행을 구분한다. 원본 계획서는 수정하지 않는다.
2. **등급 기본 구성과 옵션 변경:** 기본 구성을 고정된 선택 제한으로 해석하면 B12~B14·B16과 충돌한다. 기본값과 변경 가능 항목을 구분한다. 허니문·효도의 호텔 하향 조건은 Q05로 유지한다.
3. **허니문 2인과 출발 3명:** 사용자는 허니문을 2인 전용 여행으로 보고 3명 공동 모집 조건의 예외로 해석했다. 이를 BR13의 제안 분기로 반영한다. 과제 안내에 예외가 명시되지 않은 점과 신청 단위·확정 시점은 Q04에서 검토한다.
4. **단골 기준과 이력 범위:** 단골 판정에 완료 여행을 사용하는 것과 팝업에 완료 여행만 표시하는 것은 별개의 결정이다. 이력 범위를 P04에서 추론해 확정하지 않는다.
5. **기능과 구현 방법:** GUI·음성·문자 기능은 고객 요구이고, 웹·외부 API·프레임워크·DB 선택은 기존 팀 구현 결정이다. 서로 다른 출처를 표시한다.

## 9. 우선순위와 작업 의존성: 분석 제안

고객이 요구한 기능은 모두 개발 범위의 핵심 요구로 유지한다. 아래는 기능 삭제 기준이 아니라 상세 명세·개발 준비의 순서 제안이다.

1. **명세 선행 결정:** 가격·할인 Q01/Q02/Q06, 신청 Q03/Q04, 옵션 제한 Q05. 신청·상품 구성 시나리오의 결과를 정하는 데 직접 필요하다.
2. **영역별 명세 결정:** 문자 Q07, 음성 Q08, 이력 Q09, 계정 Q10, 상품 Q11, 입고 Q12. 해당 설명서 확정 전에 답을 반영한다. 영역별로 병행 논의할 수 있다.
3. **GUI 기능과 데이터 흐름:** 회원·상품 선택·신청·이력·직원 상품·입고를 먼저 구체화한다.
4. **외부 연동:** 음성·문자 동작을 같은 요구 범위로 유지하고 연동 시험을 병행한다. GUI 다음 음성 구현 순서는 M06에, 10월 사전 연동 시험은 계획서 일정에 근거한다.

미정 질문이 있다고 이미 명확한 요구의 분석·설명을 멈추지 않는다. 미정 값은 임의로 채우지 않고 연결된 질문 ID를 적는다. 미정에 따라 결과가 달라지는 상세 흐름은 질문 해결 후 확정한다.

**팀원 문서의 새 처리안은 별도 검토:** 등록된 품목만 입고 허용, 수량의 양의 정수 제한, 입고 내역과 현재 재고 증가의 반영 방식은 Q12의 처리 제안으로 남긴다. 문자 실패 시 이미 저장된 신청·출발 확정을 유지하는 안은 Q07의 처리 제안이다. 실패 기록·재시도라는 기존 계획서 방향은 유지하지만, 위 상세 정책을 합의된 고객 요구나 기존 팀 결정으로 바꾸지 않는다.
